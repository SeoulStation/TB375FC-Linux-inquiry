# FIRST/SECOND 표시 단계와 시계 비교

SECOND는 수집·정리 검증을 통과했지만 사용자가 사진 후 약1초 미만에 세로 명암선 깨짐을 보고했습니다. 따라서 광학 안정 성공으로 해석하지 않습니다. 화면 자동 꺼짐은 사용자와 소프트웨어 기록 모두에서 확인됩니다.

## SECOND 소프트웨어 단계

`APPLY_BEGIN`을 0초로 둔 값입니다. `ACTIVE`는 실제 사진을 촬영한 시각이 아니라 atomic 적용 호출이 성공한 뒤의 프로그램 단계입니다.

| 단계 | 적용 시작 이후(ms) | ACTIVE 이후(ms) |
|---|---:|---:|
| APPLY_BEGIN | 0.000 | -270.242 |
| APPLY_OK | 270.227 | -0.015 |
| ACTIVE | 270.242 | 0.000 |
| RESTORE_BEGIN | 5000.113 | 4729.871 |
| RESTORE_COMMIT_OK | 5605.698 | 5335.455 |
| RESTORE_VERIFIED | 5610.371 | 5340.129 |
| RESTORE_END | 5610.391 | 5340.149 |
| CLEANUP_BEGIN | 5610.399 | 5340.157 |
| CLEANUP_END | 5615.544 | 5345.302 |

적용 호출은 약270.227ms, ACTIVE부터 정상 복원 시작까지는 약4729.871ms, 복원 호출은 약605.585ms였습니다. 첫 사진이 ACTIVE 근방에서 보였다고 가정하면 사용자의 <1초 보고는 초기 활성 구간과 대응하며 정상 복원 시작보다 이릅니다. 그러나 사진 가시 시작과 깨짐을 기록한 동기화 영상·센서 자료가 없어 정확한 시점 연결이나 원인 판단은 할 수 없습니다.

일반 `puts` 출력은 버퍼링되고 단계 행은 별도 `write`로 저장됩니다. `IDLE_RECHECK_BEFORE_APPLY` 등이 파일에서 뒤에 보이는 것은 실제 실행 순서의 역전을 입증하지 않습니다. 단계는 `seq`와 `mono_ns`로 정렬했습니다.

## FIRST와의 비교

| 항목 | FIRST | SECOND |
|---|---:|---:|
| 수집 구간(ms) | 6000 | 6239 |
| trace 행 | 2 | 1750 |
| read pre/post | 0 / 0 | 311 / 311 |
| write pre/post | 1 / 1 | 564 / 564 |
| missed | 모두0 | 모두0 |
| viewer 단계 시각 | 없음 | 9개, 오류0 |
| 사용자 광학 관측 | 안정적, 자동 꺼짐 | <1초 뒤 세로 명암선, 자동 꺼짐 |

FIRST trace는 실제 write pre/post 한 쌍입니다. 시각19824.438050/19824.438140은 수집 시작19818.800에서 약5.638초 뒤이고 종료19824.800보다 약0.362초 앞입니다. 종료 인접 구간이지만 FIRST에는 단계 시각이 없어서 이 write를 off/restore로 확정할 수 없습니다.

FIRST 원 host 결과는 `Success=false`, `CleanupUnknown=true` 상태로 보존됩니다. 별도 완료 회수는 성공했고 당시 사용자 광학 관측은 안정적이었습니다. 이 세 사실을 서로 바꾸어 표시하지 않았습니다.

## kernel stream과 snapshot의 시간 한계

stream은 1536개 레코드(935282–936817)를 저장했고 수집된 레코드 내부 sequence gap은0입니다. arm부터 종료까지 약12000.912ms이며 최초 read는 APPLY_BEGIN 약391.926ms 전입니다. viewer와 stream의 read 시작/종료 시각은 소스에서 CLOCK_MONOTONIC을 사용합니다.

반면 kernel header의 timestamp와 CLOCK_MONOTONIC의 동일성은 검증되지 않았습니다. 실제 `kernel_timestamp_us×1000−read_start_ns`는 약−2.434~+4.384ms입니다. 이를 임의 오프셋으로 보정하거나 kernel timestamp를 광학 발생시각과 동일시하지 않았습니다.

read 시작 시각으로 나눈 레코드 수는 적용 전1, 적용 중33, ACTIVE 첫1초211, 그 뒤 복원 전1262, 복원 중27, 복원 검증 뒤2입니다. 이는 레코드를 읽은 구간이며 실제 사건이 발생한 구간으로 확정한 분류가 아닙니다.

전후 snapshot은 각각131046/131027B입니다. 반환된 내용을 모두 저장했어도 전체 ring 이력·정확한 전체 수집창 이력·인과관계 보장 플래그는0입니다. 후 snapshot의 kernel timestamp 범위는99047.626913~99052.529992로, 앞 snapshot과 두 파일만 비교해 전체 표시 시작을 연속 재구성할 수 없습니다. 원 stream을 함께 보아야 하며 이 경우에도 전체 이력을 보장하지 않습니다.

IO/SPI 원인은 이 보고서에서 확정하지 않습니다. 원본·영수증·상태를 수정하거나 추가 표시를 실행하지 않았습니다. 자세한 원본 pin과 수치는 동명의 JSON에 기록했습니다.
